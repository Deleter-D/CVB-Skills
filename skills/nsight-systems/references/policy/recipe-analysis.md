# Recipe Analysis Policy

Recipes are installed with the user's Nsight Systems build. The live installed recipe list is authoritative for availability.

Use recipe lookup/help for:

- which recipe to use,
- recipe options and input/output behavior,
- output files/columns,
- interpretation of recipe output.

Use deterministic report facts before SQL when the fact tool covers the question. Use bounded SQL/DuckDB for simple independent aggregations where no recipe-specific row classification, overlap math, utilization, pacing, or gap semantics are required.

Use recipe execution for:

- explicit requests to run or generate recipe output,
- analyses where recipe code encodes semantics that ad-hoc SQL is likely to get wrong,
- named recipe concepts such as synchronous memcpy/memset, async pageable memcpy, GPU gaps, utilization maps, kernel histograms, kernel pacing, graphics frame hotspot comparison, GPU VRAM usage tracing, and Vulkan/DX12 memory operations.
- multi-report comparisons where an installed recipe owns the comparison or correlation semantics.

If a question asks for straggler detection, exposed communication cost, layer-level attribution, per-iteration jitter, or communication/compute overlap, treat it as recipe/domain-tool analysis. Do not approximate those conclusions with ad-hoc report SQL unless the answer is explicitly limited to a simple supporting fact and clearly says it is not the validated recipe/domain metric.

## Command and input/output contract

When answering the generic recipe command-line form, use the top-level live help shape: `nsys recipe [<args>] <recipe name> [<recipe args>]`. For built-in recipes that take reports, show `--input <report.nsys-rep>` only when live per-recipe help lists it. Put the recipe name before recipe-specific arguments, for example `nsys recipe cuda_api_sum --input report.nsys-rep`.

For recipe input file-type questions, use the curated recipe-framework input reference in addition to live help. Some per-recipe help text says `.nsys-rep` files/directories while the installed input parser can also accept older `.qdrep` files. Mention directories separately as input locations, not file types.

Do not pass user-provided `--input`, `--output`, `--output-dir`, or `--export-dir`; the tool/script chooses the report, recipe output, and export cache. If the user asks to override those paths, decline that part and offer to run the recipe against the loaded report with outputs chosen by the tool. If the wrapper rejects those path arguments, do not retry with a direct `nsys recipe` command as a workaround.

Use `--output <directory>` and `--force-overwrite` when answering general docs questions about intentional recipe result replacement. Mention `--export-dir` only to clarify that it controls intermediate export artifacts, not the main recipe results directory, or when the user specifically asks about exports.

## Output interpretation

For standard/common recipe output questions, name the common stats-recipe files explicitly: `files.parquet`, `rank_stats.parquet`, `all_stats.parquet`, `stats.ipynb`, and `<output-name>.nsys-analysis`. Mention `rank_stats_by_device.parquet`, `all_stats_by_device.parquet`, helper files, and CSV companions as recipe- or option-dependent, not universal. Describe `.nsys-analysis` as the JSON analysis metadata entry point: it records recipe metadata, execution options/timing, and generated output inventory; it is not itself the primary performance table.

When execution returns `primary_result_files`, use those as the default files/tables to summarize. Treat `result_files` as generated data files, `auxiliary_files` as metadata/notebook/entrypoint artifacts, and `helper_files` as support files. Treat `files.parquet`/`files.csv` as input metadata, not analysis results.

When execution returns `output_profile`, use it to choose the summary shape:

- `stats`: summarize `all_stats` for aggregate questions, `rank_stats` for per-input/rank questions, and `*_by_device` for device/GPU questions.
- `analysis_rows`, `trace`, `map`, or `diff`: summarize `analysis.*` or primary result rows, usually sorted by duration or another returned preview sort.

When execution returns `expected_output_notes`, use them to explain framework conventions such as the `.nsys-analysis` entry point or optional CSV companions. If `supports_csv` is true, say CSV files can be generated by rerunning with `--csv`; do not claim a CSV file was generated unless it appears in `result_files` or `primary_result_files`. When execution returns `output_previews`, use those previews to summarize the result in prose instead of only saying that files were produced.

Do not replace this workflow with direct shell calls to `nsys stats` or `nsys recipe` unless the user explicitly asks about those raw commands. The packaged wrappers own report inputs, output locations, redaction, and follow-up schema/query commands. `nsys stats` summaries and Advanced Analysis recipe outputs can have different files and columns even when their names look similar.

## Execution failures

When execution returns `preflight`, use it to explain cheap health checks such as whether `nsys` is available, the recipe is installed, live recipe help was readable, the report input exists, and the output root is writable. Do not treat preflight as proof that the report contains the data required by the recipe; use report context/doctor or recipe failure evidence for that.

When execution returns `recipe_outcome.status == completed_no_data`, the recipe command succeeded but did not produce analysis data for the loaded report. Say that directly and use the returned guidance; do not treat an empty output directory as successful evidence for a numeric conclusion.

If recipe execution fails, do not silently replace the failed recipe with SQL. Report the failure category, stderr/error evidence, preflight findings, and repair guidance. SQL/report facts may answer a separate simple aggregation only when the original question can be answered independently without recipe-defined semantics, and the answer must label that evidence as non-recipe evidence.

For explicit recipe-run requests, exact recipe-output questions, or recipe-owned concepts such as synchronization, gaps, pacing, overlap, or utilization maps, do not present SQL as equivalent to the failed recipe.

For broad recipe memory/troubleshooting questions, use only documented levers unless a specific recipe's live help was inspected: `--filter-time`, `--filter-nvtx`, directory `:n`, `--mode none`, fewer inputs, and checking for corrupt/incomplete reports or insufficient memory/disk. Do not invent environment variables for worker counts unless the installed recipe framework documents them.

## Custom recipes and generic file questions

For custom recipe work, assist rather than authoring the recipe for the user: explain concepts, review user-provided code or errors, and suggest focused next steps.

For generic questions about Parquet files or recipe-generated notebooks, keep the answer at the workflow level unless the retrieved reference or executed output proves exact file names. Standard Parquet readers such as pandas/PyArrow are enough for "how do I access Parquet data?"
